[x]pint

Extended validation for dimensional quantities.

xpint extends Pint with semantic metadata that ordinary dimensionality does not represent: quantity kinds, factor-level designations, and affine roles for thermodynamic temperature.

With the default registry, Pint continues to define ordinary dimensions, unit conversion, contexts, formatting, and NumPy behavior. The optional angle_dimension=True registry deliberately gives plane angle a dimension and is not interchangeable with a default registry.

0.1.0b1 · public beta Python 3.12+ Pint ≥0.25.3, <0.26 BSD 3-Clause

Objective

Semantic distinctions beyond dimensionality

Dimensional analysis determines whether quantities are physically commensurable. It cannot represent every distinction an application may need to enforce when equal-dimensional values have different meanings.

xpint addresses four such distinctions:

ExpressionDimensionalitySemantics
joule + newton metre Identical Distinct kinds: energy and torque
mmol[O2]/L + mmol[NaCl]/L Identical Distinct designations: oxygen and sodium chloride
mL[plasma] / mL[whole_blood] Dimensionless Retained compartment identity after dimensional cancellation
10 K Temperature Absolute, difference, or unspecified affine role

xpint stores these distinctions with the value and validates them before an operation can discard them. An undesignated, unkinded, non-affine quantity follows Pint's ordinary behavior.

Terminology / xpint specific terms

TermMeaning
Kind What a quantity is. A named meaning that separates values sharing a dimension, so energy and torque stop being interchangeable. A kind constrains which operations are allowed; it never changes how a conversion is computed.
Designation What a quantity is of. A substance or compartment label carried inside the unit, so millimoles of oxygen and millimoles of salt have different unit identities. Matching labels cancel; differing labels remain.
Classified value A quantity carrying any of that added metadata: a kind, a designation, or an absolute or delta temperature unit. The word the error messages use. Everything else is an ordinary value and behaves exactly as it does in Pint.

Architecture / Pint integration

Relationship to Pint

xpint extends rather than patches Pint. SemanticQuantity subclasses the quantity class bound to its registry, and SemanticRegistry subclasses Pint's GenericUnitRegistry. Importing xpint does not replace Pint's process-wide application registry.

Responsibility is divided as follows:

ConcernOwnerNotes
Unit definitions, prefixes, parsingPintxpint adds a curated short-symbol module bound to one registry
Dimensional reduction & commensurabilityPintUnmodified; it gates everything else
Scale and offset conversionPintxpint decides whether a conversion is meaningful, never how to compute it
Contexts, formatting, NumPy protocolPintDelegated for ordinary values
Quantity kindsxpintDimension-constrained; as_kind / as_unkinded / has_kind
Factor-level designationsxpintPart of unit identity and cancellation, not a display label
Affine rolesxpintAbsolute / Delta / Generic, thermodynamic temperature only in v0

xpint adds explicit classification helpers and guards inherited operations. An undesignated, unkinded, non-affine quantity delegates ordinary operations to Pint; classified values add validation at operations where their metadata is relevant.

Deliberate behavioral differences

Classified quantities differ from stock Pint in a bounded set of operations where Pint does not model xpint metadata:

  • Implicit ndarray downcast of a classified value raises, where Pint emits UnitStrippedWarning and returns bare magnitudes. Unclassified values keep Pint's behaviour.
  • Supported reductions validate and convert quantity-valued initial= inputs. Unsupported out= targets reject before a unit-blind write; support is specific to each operation.
  • Operations mixing quantities from two registries are rejected explicitly.
  • Affine construction goes the other way: xpint permits 20 * degC, which a default Pint registry refuses as an ambiguous offset operation, because the role makes the multiplication unambiguous. Absolute/Delta arithmetic follows explicit role rules, and the Generic role prevents unmarked kelvin from being silently treated as a point or a difference.

The initial compatibility surface is deliberately bounded. Pandas, arbitrary Dask graph transformations, and designated pint-xarray round trips are not yet supported. Tested classified paths reject undefined propagation; untested integrations have no preservation guarantee.

1  ·  Validate meaning as well as dimension

Evaluation order

Four gates, in a fixed sequence

The concerns are distinct but not independent, so their evaluation order is part of the contract. Each check runs only after the preceding condition has passed.

01
Dimension
Pint decides whether the operation is physically possible at all.
02
Designation
Partitions the dimension map by substance or compartment. Matching labels cancel; differing ones remain in the signature even when the units cancel.
03
Affine role
For thermodynamic temperature, derived from the unit token and any kind. Evaluated before kind absorption.
04
Kind
Constrains the meaning-sensitive operations that remain valid. Stored kinds must match; an unkinded operand is not absorbed into a kinded one.

The ordering is observable. 20 degC + 5 K is rejected with an affine-role error rather than a kind error, because the Generic role of bare Kelvin fails at gate 3 before gate 4 is reached.

Performance

Performance and failure safety

xpint validates metadata per supported array operation rather than per element. Small operations pay for dispatch and semantic checks; larger out-of-place operations spend more time in the array kernel. Benchmark the operations and array sizes your application actually uses.

In-place operations have a different cost

NumPy in-place powers and unit conversions stage a temporary buffer so a failed operation leaves values, units, and metadata intact while preserving caller aliases. Classified multiplication and division also stage the resulting semantic state. This adds full-array copying and one full-size buffer; automatic reduction can require another buffer. Other duck-array backends retain Pint's mutation behavior.

Vectorized arithmetic avoids repeated Python-call overhead, but it does not eliminate staging costs. Correctness checks and transaction guarantees are retained even where a prior implementation was faster.

Use uv run python benchmarks/benchmark_pint_passthrough.py for ordinary arithmetic and uv run python benchmarks/benchmark_semantic_safety.py --backend xpint for the broader timing/allocation matrix. Compare with --backend pint using fresh processes and recorded dependency versions. Historical prototype timings are not current beta performance guarantees.

Optional angle dimensions / opt-in, off by default

Optional dimensional treatment of plane angle

SI classifies the radian and steradian as dimensionless derived units. Consequently, ordinary dimensional analysis cannot distinguish angular velocity from cyclic frequency, torque from energy, or a solid angle from a plain ratio. xpint can instead give plane angle a base dimension, with steradian derived as rad²:

Opt inconstruction time only
from xpint import SemanticRegistry

u = SemanticRegistry(angle_dimension=True)

u.get_dimensionality("radian")      >>> [angle]
u.get_dimensionality("steradian")   >>> [angle] ** 2

A default SemanticRegistry() retains Pint's dimensional treatment. The option is fixed when the registry is constructed because Pint caches dimensionality, and quantities from the two registry modes cannot be combined. There is no global switch or runtime toggle.

Gyromagnetic-ratio input normalization

Gyromagnetic ratios are commonly supplied in angular units such as rad·s⁻¹·T⁻¹ or cyclic-frequency units such as MHz·T⁻¹. A function accepting either convention must identify the input before normalizing it:

Normalize to cyclic frequencyrunnable example
def larmor_frequency(registry, gamma, magnetic_flux_density):
    """Return the cyclic Larmor frequency in megahertz."""
    angular_units = registry.radian / registry.second / registry.tesla
    cyclic_units = registry.hertz / registry.tesla

    if gamma.is_compatible_with(angular_units):
        return (gamma * magnetic_flux_density / registry.turn).to(
            registry.megahertz
        )
    if gamma.is_compatible_with(cyclic_units):
        return (gamma * magnetic_flux_density).to(registry.megahertz)
    raise ValueError("unsupported gyromagnetic-ratio units")

Angle-explicit equations use η = 1 / radian where an angular quantity must become dimensionless or combine with length. For example, phase is ηωt and tangential speed is ηωr. The background below records the mathematical convention, its consequences, and its limitations.

Standards and mathematical background

Standards context and design choice

The SI treatment of angle has changed over time. From 1960, the radian and steradian occupied a third class of supplementary units, neither base nor derived. Resolution 8 of the 20th CGPM (1995) abolished that class and interpreted them as dimensionless derived units. The Consultative Committee for Units established another working group on the question in 2013 and reported no consensus in 2021.

OptionPositionConsequence
rad ≡ 1 Status quo, and the CCU majority view in 2021. Every textbook equation holds verbatim. Torque and energy, ω and f, Gy and Sv, and lm and cd share dimensions.
radius in m/rad Considered and abandoned. Breaks πr² for the area of a circle.
[angle] with η Mohr and Phillips at NIST, Quincey at NPL, Leonard, Kalinin. What this switch implements. η enters the kinematic relations, and some familiar equations acquire it.

In the angle-explicit formulation, the present SI treatment corresponds to the convention η = 1. Introducing η preserves a separate angle dimension and changes which substitutions dimensional analysis can distinguish.

Several proposals identify quantity-calculating software as a potential use of angle-explicit equations. Quincey and Brown (2016) discuss their computational value, and Mohr, Shirley, Phillips and Trott (2022) develop unit-independent trigonometric functions with computer algebra in mind. Version 3.01 of the SI Brochure (2024) retains dimensionless angles while strengthening guidance to use explicit units where possible for quantities with the unit one.

xpint does not attempt to settle the metrological question. The switch is off by default, and the default registry retains the SI treatment. The option makes an alternative, internally consistent dimensional convention available per registry.

Rotational symmetry and conjugate quantities

The conserved quantities associated with time translation, space translation, and rotation can each be expressed as action per unit of the corresponding symmetry parameter.

Under the SI treatment, angle is dimensionless and angular momentum therefore shares the dimension of action. Quincey (2021) uses this distinction to motivate separate symbols for the action and spin interpretations. Assigning angle a dimension gives the three rows parallel dimensional forms.

Generalized force is energy per unit coordinate. Applying that relation to linear and angular coordinates gives:

Lagrangian mechanics generalises it: for any coordinate q, the generalized force is ∂W/∂q and the conjugate momentum is ∂L/∂q̇, with dimensions [energy]/[q] and [action]/[q]. One rule produces newton and kg·m/s for a length coordinate, and J/rad and J·s/rad for an angular one. So xpint spells Torque as joule / radian and AngularMomentum as joule * second / radian under this registry. newton * meter carries no angle, which is exactly why it never separated from energy.

Dimensional constant η = 1 rad⁻¹

The arc-length relation connects angle and length, so the angle-explicit formulation introduces η at that boundary. Related rotational equations inherit the same constant:

Consequences of the dimensional choice

a  ·  Published angular and cyclic conventions

The proton gyromagnetic ratio is quoted both as 2.675×10⁸ rad·s⁻¹·T⁻¹ and as 42.58 MHz·T⁻¹. These values describe the same physical constant using angular and cyclic conventions. The normalization example above shows why an API may need to distinguish them.

CODATA 2022 publishes the two forms as separate named constants:

CODATA 2022 entryValueUnit as publishedDimension
proton gyromag. ratio 2.675 221 8708 × 10⁸ s⁻¹ T⁻¹ [T]⁻¹[…]
proton gyromag. ratio in MHz/T 42.577 478 461 MHz T⁻¹ [T]⁻¹[…] — identical

The values differ by 2π. Under the SI dimensional treatment, their units differ only by the scale factor between hertz and megahertz, so the convention is carried by the entry name rather than dimensionality.

rad does not appear in the CODATA units column for the angular entry. A value transcribed directly from that table therefore does not contain enough unit information for dimensional dispatch.

Under an angle registry that vocabulary exists, but the standard will not supply it for you: transcribing CODATA verbatim still gives s⁻¹ T⁻¹, which stays interchangeable with MHz T⁻¹. You have to choose to write the radian:

Explicit angular annotationverified
dim("1/second/tesla")     == dim("megahertz/tesla")   >>> True   # as published
dim("radian/second/tesla") == dim("megahertz/tesla")   >>> False  # as meant

Writing rad into the unit records the caller's interpretation. The angle registry makes that annotation enforceable; under a default registry both comparisons return True.

b  ·  Steradian as a derived angular unit

Pint defines steradian = radian ** 2 in default_en.txt. Under the SI treatment both sides are dimensionless. With a plane-angle dimension, the same definition gives steradian the dimension [angle]².

Dimensionless angleoperations permitted
np.sin(1 * sr)
>>> 0.8414709848 dimensionless

1 * sr + 1 * rad
>>> 2.0 steradian
Plane angle, solid angle, and scalar values share one dimensionality.
[angle]rejects
np.sin(1 * u.sr)

    cannot convert [angle] ** 2
    to [angle]

1 * u.sr + 1 * u.rad
>>> DimensionalityError
A solid angle has dimension [angle]², so neither operation satisfies the required dimensional relation.

Why rad² rather than a second base dimension. For a small patch on a sphere of radius r subtending orthogonal plane angles dθ₁ and dθ₂, the local arc relations give:

Local spherical patchradius and η cancel
dx = η r dθ₁        dy = η r dθ₂

dA = dx dy   = η² r² dθ₁ dθ₂
dΩ = dA / (η² r²) = dθ₁ dθ₂      # no η, no r

The resulting solid angle is the product of the two plane angles, with no remaining length or dimensional constant. For example, a 1 mrad × 1 mrad beam subtends 1 µsr.

This cancellation motivates deriving solid angle from plane angle rather than introducing a second constant. The relation Ω = θ₁θ₂ no longer crosses between length and angle once the radius has cancelled.

Two additional consequences support that representation:

  • Higher-dimensional generalization. The angle subtended in n dimensions has dimension [angle]n−1: 2π rad on the circle, 4π rad² on the sphere, and 2π² rad³ on S³.
  • Small-angle optical calculations. Under rad², solid_angle = theta_x * theta_y has the expected solid-angle dimension without an additional conversion constant.

Kalinin treats plane and solid angle as different quantity kinds. They are already non-comparable in this representation because rad and rad² have different dimensions. Other equal-dimensional meanings may still require kinds: moment of inertia in kg·m²/rad² and mass-area per solid angle in kg·m²/sr share a dimension. Both operands must carry kinds for that additional distinction to be enforced.

This is a design choice rather than a theorem. An independent [solid_angle] with a second constant is also self-consistent and more discriminating. Identifying sr with rad² removes distinctions of the form [solid_angle] − 2[angle], including torsional stiffness versus energy per solid angle and angular variance versus solid angle. xpint follows the sr = rad² treatment used by Leonard and Kalinin and retains η as the only added dimensional constant.

A bare Python number does not enter the registry. For example, np.sin(90) interprets 90 as radians. Once the value is represented as a quantity, the registry can distinguish a dimensionless argument from an angle:

These cases share an implicit angular convention. With an angle dimension and η, the convention becomes part of dimensional validation.

Wave phase. A phase must be dimensionless before it enters an exponential. Under this registry ωt has dimension [angle], while ηωt is dimensionless. Consequently, exp(i(kx − ωt)) uses exp(i·η·(kx − ωt)) when both k and ω are angular quantities.

Buckingham π analysis with η

Adding an angle dimension raises the rank k of the dimensional matrix where angular quantities appear. Adding η raises the variable count n by one, leaving n − k unchanged and preserving the number of Buckingham π groups.

The hazard runs one way only. Omit η and the analysis silently over-constrains. On the simple pendulum, by matrix rank:

Treatmentnkπ groupsResult
SI, angle dimensionless532T√(g/L) and θ₀ — correct
[angle], η omitted541amplitude cannot appear — wrong
[angle], η declared642T√(g/L) and ηθ₀ — correct

The failure mode is a plausible result rather than an error, so η must be admitted as a dimensional constant exactly as c or kB would be.

Pint's own m_as(unit) already does the job, so xpint adds no stripping API: anything that turned an angle into a number without naming a unit would guess radian, reinstating the surprise the switch exists to remove. Going the other way is ordinary multiplication, x * u.radian. The only code this needed was an error message that names the alternatives instead of leaving a bare dimensionality failure.

Prior art and references

Boost.Units has represented plane and solid angle as base dimensions since 2007 and provides corresponding trigonometric support. Simscape documents the opposite choice, defining rad as m/m so trigonometric functions accept angular arguments directly and torque in N·m remains dimensionally equal to energy in J. xpint exposes the choice per registry.

Scope: v0 supports Pint's stock definition set, at construction time, with no runtime toggle and no custom contexts. The angle registry scopes its internal redefinitions so the caller's on_redefinition policy remains in force for later definitions; on_redefinition="raise" is supported. Values from scoped registries can be pickled; select an xpint application registry with matching definitions and angle mode before unpickling. examples/angle_dimensions.py exercises the public behavior through both registry modes.

Status

What exists today

The semantic foundation and factor-level designation algebra are implemented and tested. Kinds, designations, affine roles, pickling against a selectable xpint application registry, and a bounded NumPy, Dask, xarray, and masked-array compatibility matrix are in place. Unsupported operations raise rather than discarding metadata.

The angle_dimension=True registry is implemented within the scope stated above: stock definitions and construction-time selection, with no runtime toggle. The steradian is derived as rad², and the angle-specific kind catalogue uses conjugate dimensions for torque, angular momentum, and moment of inertia.

0.1.0b1 is the first public beta. This page describes the behaviour implemented for 0.1.0b1; beta status means the API and the supported compatibility surface can still change.

xpint extends Pint and does not modify Pint source or its application registry. Pint remains authoritative for ordinary unit definitions and conversion; the optional angle registry deliberately supplies an alternative dimensional treatment of plane and solid angle. The comparisons on this page are behavioral observations against Pint 0.25.3 and identify distinctions outside Pint's scope.
